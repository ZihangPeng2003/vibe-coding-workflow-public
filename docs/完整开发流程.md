# 从想法到发布：网页与桌面应用开发流程

版本：2026-10-12。网页与 macOS 等桌面应用同等覆盖。

本文件是给人读的说明。AI 实际执行的规则在仓库根目录的 [`AGENTS.md`](../AGENTS.md)，模板在 [`templates/`](../templates/)。

**你描述想法、判断体验；AI 负责调查、方案、实现、真实验证，以及该产品已授权的部署和公布。** 不需要你先学会框架、数据库，也不需要记一组命令。

**描述想法 → 明确用户任务与范围 → 规格确认 → 视觉和交互设计 → 完整功能 → 反馈迭代 → 验收 → 部署／分发 → 公布与反馈。**

## 每个阶段你会得到什么

| 阶段 | AI 做什么 | 你需要决定什么 | 完成依据 |
|---|---|---|---|
| 1. 想法与范围 | 看现状，整理谁在什么场景解决什么问题；给出本轮默认方案和不做项 | 主要用途、使用者、关键取舍 | 能用普通话说清产品目标和第一个主流程 |
| 2. 规格与方案 | 写出功能、状态、数据路径、技术方案和验收标准 | 确认这份方案（Spec Lock）；数据与费用上的重要决定 | 范围明确、任务和验收一一对应、你已明确批准实施 |
| 3. 设计方向 | 给出可查看的草图或界面，写下视觉与交互约定，处理中文内容 | 没有既定方向时从具体方案里选 | 视觉与交互规则足够明确，选择和待确认项有记录 |
| 4. 第一个完整功能 | 把界面、业务规则、真实存储和反馈连成一条路径 | 实际操作并给出具体反馈 | 一条从输入到再次读取的真实路径能工作 |
| 5. 迭代与完善 | 按既定范围补功能，按你的反馈修改并验证 | 当前版本哪里不符合期望 | 范围内的重要反馈已处理；没反馈就保留待确认 |
| 6. 验收 | 做必要的测试、界面操作和变更审查，保存证据 | 体验是否接受；必要的范围取舍 | 该验的有证据，没验的看得见，没有未处理的阻断问题 |
| 7. 部署／分发 | 准备精确版本、发布材料和回退方案；执行已授权的发布 | 还没定的目的地、受众或新费用 | 网站的实际状态或安装包的状态已核验 |
| 8. 公布与反馈 | 准备真实介绍、截图和使用入口；执行已授权的公布，整理反馈 | 新渠道、新受众、新内容 | 草稿或发布结果记录准确，反馈进入下一轮 |

已有项目从当前进度继续。一个错别字或孤立的 Bug 直接修复并适度验证，不重走八个阶段。阶段之间可以返回，但不能用一张截图证明全部功能完成。

## 网页和桌面应用分别怎么落地

| 环节 | 网页／网页应用 | 桌面应用（macOS 等） |
|---|---|---|
| 界面 | 浏览器页面、中文排版、窄屏、触控与键盘 | 真实窗口、菜单与快捷键、设置、主题、焦点与辅助功能 |
| 数据 | 单机用本地保存；多用户、共享数据或需要保密的接口才建服务端 | 直接用本地数据层；需要云同步或远程账户才加服务器 |
| 第一条完整功能 | 输入 → 校验 → 保存 → 刷新后仍能读取 | 输入 → 保存 → 退出 → 重新打开仍能读取 |
| 真实验证 | 浏览器里操作、真实请求与存储、错误恢复；上线后再验一次 | 原生窗口里操作、权限被拒绝时的表现、保存与退出重开；安装包另验 |
| 发布 | 沿用已有托管，核对精确版本、访问范围、域名与费用 | 自用、有限测试、公开下载或商店；按途径核对签名、公证、安装与升级 |

技术选择由 AI 在检查项目后给出有依据的默认方案，已有技术栈先保留。不会为了“前后端齐全”给一个离线的单机工具强加云服务器。

## 怎么判断“达到我满意的状态”

每次给你一个能操作的版本，让反馈落到具体场景：什么行为、哪个界面、希望怎么变。先处理主任务受阻、数据问题和可读性，再迭代风格细节。没有回复不算满意。

完成状态分成四条单独记录：

1. **功能与质量**：通过、失败、未验证，各有证据。
2. **你的体验**：明确接受的版本、待确认的、仍需修改的。
3. **部署／分发**：本地、预览、上线、安装包各自的准确状态。
4. **公布**：文案草稿、实际发出的结果和链接。

你接受了外观，不代表数据错误可以忽略；测试全部通过，也不代表你已经接受了外观。范围变化时更新相关验收，普通的小修改不重做一套规划。

## 从下一个想法开始

直接说：

> 我想做一个网页／macOS 应用，主要帮我解决……，给……使用。我不懂代码，请按项目里的 AGENTS.md 流程推进，并结合每次实际改动解释一个概念。

AI 会先把想法变成一份具体方案给你看，你确认后再做。新的费用、访问范围和公布渠道需要你明确同意；已经同意过的同一范围不会反复确认。
